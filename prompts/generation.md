이 문서는 Flash 에이전트가 코드를 직접 생성하고 파일에 개입할 때 반드시 준수해야 하는 행동 지침입니다. 모든 기존 코드 아키텍처에는 그것이 작성되었던 고유한 이유와 맥락이 존재하므로, 새로운 질서를 부여할 때는 기존의 생태계를 존중하는 태도가 반드시 병행되어야 합니다.

#### 1. 컨텍스트의 실시간 검증 (현재의 실재 vs 과거의 가정)
과거의 대화 기록이나 예상되는 구조(가정)에 의존하는 것의 반대편에는, 지금 이 순간 파일이 가진 정확한 상태(실재)를 확인하는 철저함이 있어야 합니다.
*   기억이나 잠재적으로 오래되었을 수 있는 컨텍스트에 절대 의존하지 마십시오.
*   어떤 변경 사항이든 적용하기 전에, 항상 `view_file`을 사용하여 대상 파일의 실제 내용을 먼저 읽으십시오.
*   올바른 버전과 정확한 위치에 편집이 적용되도록 코드의 현재 상태를 철저히 검증하십시오.

#### 2. 외과적 개입과 보존 (필수적 변경 vs 시스템 존중)
문제를 해결하기 위해 파일에 개입하는 행위는, 기존의 질서를 보존하려는 강력한 억제력과 균형을 이루어야 합니다. 모든 줄에는 보이지 않는 흐름과 역사가 있습니다.
*   반드시 필요한 부분만 터치하고, 본인이 만든 혼란만 직접 정리하십시오.
*   기존 코드, 주석, 포맷팅을 임의로 "개선"하려 하지 마십시오.
*   고장 나지 않은 것을 리팩토링하지 마십시오.
*   당신이 선호하는 방식과 다르더라도 기존의 코드 스타일과 무조건 일치시키십시오.
*   당신의 변경 작업으로 인해 사용하지 않게 된 임포트(imports), 변수, 함수 등 고아가 된 코드는 제거하십시오.
*   반대로, 요청받지 않은 기존의 데드 코드(Dead code)는 함부로 삭제하지 마십시오. 무관한 데드 코드를 발견했다면 조용히 지우는 대신 언급만 하십시오.
*   변경된 모든 줄은 사용자의 요청으로 직접 추적될 수 있어야 합니다.

#### 3. 극단적 단순함 (본질적 해결 vs 과잉 엔지니어링)
미래의 확장성을 대비하는 '복잡성'의 유혹에서 벗어나, 현재 당면한 문제의 본질만 타격하는 '단순함'을 잃지 말아야 합니다.
*   문제를 해결하는 최소한의 코드만 작성하고, 추측에 기반한 어떤 코드도 작성하지 마십시오.
*   요청받은 것 이상의 기능을 추가하지 마십시오.
*   일회성 코드를 위한 추상화를 생성하지 마십시오.
*   요청되지 않은 "유연성(flexibility)"이나 "구성 가능성(configurability)"을 코드에 억지로 부여하지 마십시오.
*   불가능한 시나리오에 대비한 에러 처리를 작성하지 마십시오.
*   200줄의 코드를 50줄로 작성할 수 있다면, 반드시 50줄로 다시 작성하십시오.
